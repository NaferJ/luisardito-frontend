# Windsurf Agent Rules — luisardito-frontend

These rules are mandatory. Follow them on every task in this repository.
Keep this file in sync with `.github/copilot-instructions.md` and
`.devin/rules/luisardito-frontend.md` — they encode the same house rules for
different tools.

## 0. Working branch

- One concern per branch. Name branches `refactor/...`, `fix/...`,
  `feat/...`, `chore/...`, `test/...`, or `docs/...` matching the change type.
- Never commit directly to `main`. Never open a PR or commit unless explicitly
  told to.
- The agent makes the change, runs the full verification gate (below), and
  reports the diff plus command output WITHOUT committing.

## 1. Language: English only

- All code, comments, logs, commit messages, and new identifiers MUST be in English.
- Never write Spanish in the codebase.
- When editing a file that has Spanish comments/strings, translate them to
  English as part of that change. Do not leave mixed-language files.

## 2. No emojis

- Never add emojis to code, logs, comments, commit messages, or docs.
- When editing a file that contains emojis, remove them and replace with plain text.

## 3. Logging

- There is no logger utility. Do NOT add `console.log` debug noise.
  `console.warn` / `console.error` are acceptable for genuine warnings/errors only.
- Never log secrets.

## 4. Environment / dev setup

- No `.env.example` exists yet. If env vars are introduced, create `.env.example`
  with safe placeholders and keep it as the single source of truth.
- Keep `.gitignore` excluding `node_modules`, `.env*` (except the example),
  `.next`, build output. Never commit real secrets.

## 5. Architecture & conventions

- This is **Next.js 16 App Router**, not Pages Router. Use `src/app/` for routes,
  layouts, and pages. There is no MVC layer and no Express.
- Small, single-purpose modules. Strict TypeScript — no `any`, no non-null `!`
  to silence the compiler. Prefer precise types.
- Use the **`@/*` → `src/*`** path alias for imports, not long relative paths.
- Keep **pages and layouts thin**; extract UI into `src/components/*` and logic
  into `src/lib/*` as the app grows.
- **Next.js 16 breaking changes:** `params` and `searchParams` are **Promises**
  in Server Components — always `await` them. Use the global `PageProps<'/route'>`
  and `LayoutProps<'/route'>` helper types (no imports needed, generated by
  `next dev` / `next build` / `next typegen`).

## 6. Frontend conventions

- Default to **Server Components**. Only add `"use client"` when you need state,
  effects, event handlers, or browser APIs. Keep client components small and
  leaf-level.
- **Tailwind CSS v4** is configured via `@tailwindcss/postcss` in
  `postcss.config.mjs` and imported with `@import "tailwindcss"` in
  `src/app/globals.css`. Do not add a `tailwind.config.js` — v4 is config-less
  by default; use `@theme` in CSS for custom tokens.
- Use `next/font` for fonts (Geist is already set up in `src/app/layout.tsx`).
  Do not load fonts via `<link>` tags or CSS `@import`.
- Use `next/image` for images, `next/link` for internal navigation.
- Do not add CSS Modules unless Tailwind utilities are genuinely insufficient.
- Do not install UI libraries (shadcn, MUI, Chakra, etc.) unless explicitly asked.

## 7. Commits (Conventional Commits, English)

- Format: `type(scope): subject`. Types: `feat`, `fix`, `docs`, `style`,
  `refactor`, `perf`, `test`, `chore`, `ci`.
- Never touch the sibling repos (`poxyram-backend`, `luisardito-shop-backend`) —
  separate projects.

## 8. Scope discipline

- Make only the change requested for the current step. Do not refactor
  unrelated files.
- If a task is ambiguous, state your assumption before proceeding.

## 9. Verification gate (run on every change)

The agent must run all of these and report their output before handing back:

- `npm run lint`
- `npm run build`

All must be green. **Do NOT run `npm run dev`** — the user runs the dev server
themselves. No test framework is set up yet; when tests are added, update this
section.

## 10. Pull requests

- PR descriptions MUST follow the repo template at
  `.github/pull_request_template.md`
  (What / Why / Scope-Non-goals / Verification / Rollback).
- PR titles and descriptions MUST always be written in Markdown format.
- Keep PRs small and single-concern.
